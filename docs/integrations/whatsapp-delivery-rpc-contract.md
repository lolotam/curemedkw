# WhatsApp delivery reservation and completion

Migrations `20261103002200_whatsapp_delivery_claim.sql` and `20261103002300_whatsapp_delivery_finish.sql` add service-only reservation/completion/expiry to the existing paid expansion. They do not activate deployed payment writers, routes, credentials, pairing, a scheduler or a provider send. All test accounts and attestations are synthetic. These are incremental foundations, not a full SQL freeze or feature acceptance.

## Authority and lock order

`wa_claim_delivery(p_job_id uuid, p_actor_kind text, p_request_deadline timestamptz, p_actor_id uuid DEFAULT NULL)` accepts `worker` with a null actor, or `admin` with a real admin role row. A future HTTP handler must obtain that actor through `auth.getUser` and the real role lookup; a browser-supplied UUID or actor kind is never authoritative. Only service_role may execute any of these public wrappers. Browser roles cannot call them; service_role cannot directly update protected job tables. No SQL decrypt or arbitrary patch function exists.

Claim takes settings SHARE, account UPDATE/SKIP LOCKED, the paid event/outcome UPDATE, then job UPDATE. A null job chooses one due unparked job on the current provider/account; explicit job IDs still undergo every gate. A missing account slot may be created even on refusal: claim is mutating, not a health probe. A database try-advisory lock serializes only missing-slot bootstrap; an existing slot bypasses INSERT so an ON CONFLICT index wait cannot defeat SKIP LOCKED. Account contention refuses rather than granting a second token. The job binding is rechecked against the actual locked slot. SQL waits are not an HTTP timing guarantee; the future endpoint must enforce its own request budget. A finite server-owned deadline may be at most 55 seconds ahead and must retain at least 12 seconds after locks for the 10-second provider request and persistence allowance.

Expiry is a separate bounded account-to-job transaction, never nested after a job lock followed by an event lock. Finish takes account, job, attempt, and never takes settings afterward. Settings/credential/provider changes take settings first; active account ownership blocks credential rotation/provider activation until explicit finish/expiry. Transactions end before any network operation. No transaction performs HTTP. The existing broad coupon-table SHARE cost in the shared payment owner is unchanged and remains part of final assembled contention review.

## Claim policy

- All classes honor current integration/provider/account, due time, attempts, order cancellation/refund, and one in-flight job per account. A known provider ID or prior possible/accepted dispatch cannot gain a new ordinary claim from a state-only reset. History must exactly match the counter and contain only finished, explicitly proven retryable `not_accepted` attempts before an automatic retry.
- Automation requires the recorded durable outcome, matching expanded event and strict evidence, current automation enablement and at least one currently enabled audience among its immutable audience labels. Stale scheduler heartbeat after enablement does not block enqueue/claim or lose durable work.
- Paid legacy jobs require the recorded legacy owner and current canonical buyer/admin audience switch. Those switches project the legacy `order_paid`/`admin_new_order` configuration; the migration-time legacy_events snapshot is not reread as a later paid-event switch. Legacy does not require durable GET evidence, automation enablement or heartbeat. Recorded null/unresolved accounts are not rebound. Pre-migration baseline compatibility and request-backed shipped/old-shape event context remain separate unfinished facade/activation work. A bare request UUID does not prove which legacy event was approved.
- Manual/test require an existing matching server-created request with an admin actor, provider send readiness and the global integration switch. They do not depend on automation/heartbeat. Enqueue/authentication of these requests is a later slice; the SQL fixtures explicitly seed them and do not prove that endpoint.
- Old-provider/account work parks without rerouting or changing rendered content. Explicit integration/automation/audience pause parks with a visible reason. Cancellation/refund cancels only unclaimed work. No message already in flight can be recalled by a later cancellation.
- An encrypted credential for the active server-owned binding is required. Evolution additionally requires the matching currently connected instance/account and positive session generation. Readiness's expiring activation proof is not a five-minute lifetime for established delivery. Media must be ready, Evolution-owned and bound to that instance; Postora media obtains no claim.

A received successful reservation creates one fresh attempt token, increments the count, stores the credential binding/session generation, changes the job to sending and reserves a 45-second account lease. The job's token/expiry remain recorded after completion so a matching late definitive result can be recognized. Account spacing is at least one second at claim and again after slot release, conservatively separating subsequent provider requests even if the prior request started long after its reservation.

Successful claim response is **INTERNAL, SECRET-BEARING**: exact keys `claimed`, `job_id`, `attempt_token`, `attempt_count`, `lease_expires_at`, `provider`, `account_identity`, `credential`, `session_generation`, `recipient`, `body`, `job_class`, `media`. Credential is the encrypted `wa_credential_document` tuple captured in the same transaction. Media is null or the bounded private-object metadata. The backend must decrypt/validate in memory and must not log or return this response to a browser. Malformed/lost responses never authorize sending. Decryption/local preparation failure after reservation does not justify reclaiming; finish conservatively or let expiry require review. No process-local lock substitutes for this durable reservation.

Refusal response is exactly `{claimed:false,job_id,code,retry_at}` without PII or credentials. Codes include no_due_job, account_busy, account_paced, lease_expiry_required, deadline_insufficient, job_not_due, job_changed, delivery_history_requires_review, provider_changed, account_changed, integration_paused, automation_paused, audience_paused, order_missing, order_cancelled_or_refunded, payment_owner_mismatch, legacy_event_context_required, manual_request_required, credential_migration_required, credential_missing, session_not_connected and media_not_ready. The future transport must parse the closed set and never treat a truthy/unknown response as authority.

## Completion, retries and unknown results

`wa_finish_delivery(p_job_id uuid, p_attempt_token uuid, p_outcome jsonb)` requires the current exact attempt token and returns the SQL-owned safe summary. Outcome shapes match the provider boundary: `{kind:'accepted',providerMessageId}`, `{kind:'uncertain',code}`, or `{kind:'not_accepted',code,retryable,retryAfterSeconds?}`. Unknown fields, missing/blank IDs, arbitrary codes and invalid hints are rejected. Code strings come from a fixed vocabulary; provider bodies/messages/endpoints cannot be persisted through this interface. A lost or rejected completion is never permission to send again.

Acceptance is provider acceptance only. Delivered/read/rejected acknowledgment mapping is not implemented by these migrations. Existing terminal accepted/delivered/read/failed facts cannot regress through a later HTTP result. Duplicate completion is harmless; a token from an older explicitly replaced attempt cannot alter the current attempt. A matching late accepted result can resolve an expired/uncertain attempt, retaining a separate expiry and late-result audit. Later local/proven-not-accepted results cannot turn expired uncertainty into a queued retry. Contradictory acceptance/uncertainty after a scheduled safe rejection stops that retry for review. A provider ID already assigned to another job becomes visible review without binding two jobs or granting a resend.

Only the explicit service-attested `wa_provider_not_accepted` classification with retryable=true permits automatic retry: after attempt1, at least60 seconds; after attempt2, at least300 seconds; Retry-After is a lower bound. The current captured Evolution/Postora adapters do **not** emit this proven transient class; 429/5xx/unknown-side-effect behavior is not invented as safe rejection. SQL's retry mechanics are exercised with synthetic evidence. Hints beyond the supported0..86400-second range are rejected rather than shortened. Permanent/session/validation failure and attempt3 exhaustion go to needs_review, as the approved specification requires. The older unintegrated pure policy's exhausted=>failed implementation must be aligned before delivery-runtime integration; this contract does not adopt that stale divergence.

`wa_expire_delivery_leases(p_job_id uuid DEFAULT NULL)` mutates at most100 expired account slots with SKIP LOCKED. Sending becomes needs_review/uncertain and never queued; unfinished attempt audit is closed, account ownership released, and an append-only expired transition is retained. Repeated expiry changes no second attempt. It returns only `{expired:count}`. It is not a read-only operational probe. No ordinary retry authority exists for uncertain/accepted work. Explicit audited staff retry, duplicate-risk consent, current-provider requeue and reconciliation are future contracts, not implied by service_role or needs_review.

Safe completion summary keys: job_id, state, attempt_count, provider_message_id, due_at, safe_reason, parked_reason, updated_at, changed, conflict. It carries neither recipient/body nor credentials/token. Transition history is private and append-only through these wrappers; no direct service/browser access is granted.

## Evidence and remaining gates

`supabase/tests/whatsapp/delivery.sql` exercises actual roles and actual shared owner/strict evidence/expansion, token/lease/history binding, account pacing, safe retry bounds, unknown/late outcomes, provider-ID collisions, class gates, media refusal and instance generation. Controlled database timestamps advance lease/backoff without sleeping; no native provider result is asserted. The integration harness also forces event repair versus claim, simultaneous account claims and credential rotation versus active reservation, alongside retained payment/Shipa/expansion races and schema compatibility.

Still required: authenticated runtime delivery/facade, no-HTTP-before-commit and request/batch budgets, supported enqueue/manual/test/shipped context, acknowledgment ingestion/message mapping, retry/requeue authorization, connection-generation operations/webhook auth/media/inbox/full donor parity, real scheduler, payment endpoints/recovery/protected-writer wiring, admin UI/operating controls, final assembled Astra/tests, approved deployment and deferred native/live proofs. Ministry hold, unchanged pricing/email behavior and separate production migration/merge/customer-message/pairing/payment gates remain.
