# Shipa credential protection and diagnostics RPCs

Migration `20261103001700_shipa_credential_readiness.sql` extends the new Shipa feature only. All public functions below are service-role-only. An Edge handler must authenticate the session with `requireShipaAdmin` and use its verified actor; a browser-provided UUID is never actor authority. No RPC performs HTTP, enables the integration or confirms merchant service entitlement.

## Credential changes

`shipa_save_settings(_expected_revision integer, _settings jsonb, _credential_change jsonb, _actor_id uuid)` keeps the settings and encrypted-envelope contracts in [shipa-settings-rpc-contract.md](shipa-settings-rpc-contract.md). It locks the integration row before credential changes. The previous storage body is private and has no direct caller grant. Settings-only saves and disabling with a null credential change remain possible while work is unresolved.

Replacement/removal is refused with SQLSTATE `55000`, exact safe token `shipa_credential_in_use`, when any non-created shipment in that environment has possible-dispatch evidence, including its private permanent submission marker. A changed public display state or reset attempt fields cannot remove that protection. Another environment remains independently configurable. Resolved `created` shipments do not block key changes; created means a provider booking reference was accepted, not delivery completion. There is no unknown-result retry or recreate authority.

Settings conflict remains `40001`. Every successful save advances the settings revision exactly once. Encryption/decryption stays outside SQL, and HTTP stays outside locked transactions. A new key must be bound to the integration ID read by the server, the selected environment and current master-key version. The existing read-only loader returns the exact loaded credential revision/fingerprint required by submission begin.

## Read-only provider observations

`shipa_record_provider_observation(_expected_revision integer, _environment text, _observation jsonb, _actor_id uuid)` records a result generated by the authenticated server's read-only provider probe. The endpoint must reject caller-supplied observation/proof/ciphertext fields. SQL cannot prove that remote HTTP ran; its service-only grant is a second boundary, not a substitute for that handler.

The observation has exactly five fields:

| Field | Successful probe | Failed probe |
| --- | --- | --- |
| `credentialFingerprint` | SQL fingerprint of the key actually loaded | Same |
| `countryCode` | `"KWT"` | `null` |
| `cities` | 1–5000 names, each trimmed length 1–120 | `[]` |
| `code` | `null` | A permitted fixed adapter failure code |
| `verified` | `true` | `false` |

Permitted failures: `timeout`, `network_error`, `redirect_refused`, `not_found`, `unauthorized`, `forbidden`, `rate_limited`, `server_error`, `unexpected_status`, `malformed_response`, `invalid_response`, `response_too_large`. Local configuration refusal is not a successful remote observation. A health result with status `ERROR`, or a country result without exact KWT identity/nonempty cities, must not become successful verification; use a fixed `invalid_response` observation if a remote response was obtained but unusable.

The server should load settings and credential, call the actual fixed-origin `ShipaClient.health()` and `getCountry("KWT")` sequentially with the same key/environment, then pass only normalized facts. No order creation occurs. Success requires health `OK` and a valid KWT directory. SQL deduplicates/sorts trimmed names and compares the saved origin area case-insensitively. It checks the expected settings revision and current envelope fingerprint under locks; `40001` means the diagnostic must be repeated explicitly against current configuration. No automatic retry is implied.

The latest observation, including a failure, replaces the previous one. Its lifetime is five minutes. Any settings revision or key-envelope change makes it stale. Recording returns exactly `{recorded:true, origin_city_matched:boolean, remote_probe_ok:boolean}`. It never changes settings revision or enablement.

## Scheduler receipts

`shipa_record_scheduler_ok(_run_id uuid, _environment text, _credential_fingerprint text)` records completion of one authenticated scheduler run, including an empty queue. The future worker handler may call it only when `authorizeShipaWorker` returns source `scheduler`, after the correct runtime key has actually loaded and the bounded run succeeds. Service nudges must never call it. Scheduler custom header is `x-shipa-dispatch-token`; the deployment anon JWT additionally provides router admission. SQL does not authenticate those headers itself.

The environment must still be active and the loaded key fingerprint current. A new server-owned run UUID records its server timestamp and updates `worker_last_ok_at`; replay of that UUID returns the original timestamp without refreshing health. A reused UUID with different binding conflicts. This RPC does not advance settings revision. Its response is exactly `{run_id, recorded, last_ok_at}`. A transport-ambiguous write may be replayed only with the same run ID.

## Safe readiness projection

`shipa_read_readiness(_actor_id uuid)` returns exactly:

```text
{
  settings_revision, active_environment,
  environments: {sandbox: <environment readiness>, live: <environment readiness>},
  scheduler: {last_ok_at, current}
}
```

Each environment contains `credential_present`, `configuration_ready`, `probe_current`, `credentials_verified`, `origin_city_matched`, `last_checked_at`, `safe_code`, `service_entitlement`. Booleans are observations, not activation permission. `configuration_ready` uses the saved warehouse/service/parcel rules. `service_entitlement` is always `"unconfirmed"`; a directory vocabulary or valid API key does not establish Next Day entitlement. `safe_code` is a current fixed failure, null on a current successful probe, or `credential_missing`, `not_verified`, `verification_stale`. Old probe timestamps remain visible when stale. No directory, fingerprint, key, nonce or ciphertext is returned.

Scheduler `current` requires a matching active-environment/key receipt at the exact stored heartbeat and age at most three minutes. It does not prove that a shipment was booked. Manual booking's scheduler-independent behavior and automatic-mode gating remain separate activation/runtime contracts.

The existing `shipa_read_settings` projection remains unchanged, including its null sandbox/live `verification` placeholders; consumers use this separate readiness RPC for diagnostics. New private observation/run tables have RLS and no direct service/browser grants. No baseline schema-level/default privilege change is made. These are pre-release, unapplied contracts; full SQL freeze and production migration approval remain outstanding.
