# Curemed administrator pairing endpoint

This source adds an isolated pairing card to `/admin/whatsapp`, using the existing runtime-aware Supabase administrator session and a separately authenticated backend. The shared service/instance allocation is recorded in `shared-evolution-project-routing.md`. Application deployment, actual device pairing and full WhatsApp provider/messaging/automation acceptance are not established by this source checkpoint.

## Server authority and requests

`whatsapp-pairing/index.ts` registers `createEvolutionPairingHandler`. POST accepts exactly `{action:'status'}` or `{action:'connect'}` with a 4096-byte streamed cap. Unknown fields/query parameters, foreign browser origins and malformed requests are refused. The bearer is verified using the existing `auth.getUser` plus `user_roles(admin)` helper. An absent/malformed bearer returns 401; a false helper result returns 403, including resolved SDK errors; rejected auth transport returns a fixed 503. No service-role, anon-key, body actor, cookie or browser instance/provider selection bypass exists. OPTIONS performs no auth/config/provider work. All answers use `Cache-Control: no-store`.

The instance is the server constant `curemed`. After authorization and valid input, the backend reads only `CUREMED_EVOLUTION_URL` and `CUREMED_EVOLUTION_API_KEY`. URL must be the exact trusted internal origin `http://curemed-evolution:8080`; the key must be Curemed's independently provisioned instance token. No Evolution master, legacy variable, Postora credential or alternate-origin fallback is used. The browser supplies neither value and receives neither value.

Exactly two provider requests exist: GET `/instance/connectionState/curemed` and GET `/instance/connect/curemed`, with the server-held `apikey` header. There is no create/reset/restart/logout/delete/send/history/contact route or generic proxy. The existing `curemed` instance is provisioned by the infrastructure operator, not created by a website. Future full-port connection setup must retain that ownership rather than falling back to a master key to run its older create method.

Native redirects are refused. Provider header/body waiting is capped at 10000 ms and 512 KiB; a 15000 ms request fence covers auth/body/provider waiting. Already-aborted calls cannot start provider work. Underlying SDK/network cancellation is not claimed: late results are observed/disposed, never allowed to start a later provider operation or return a QR. Stream caps/deadlines do not depend only on Content-Length or an injected fetch honoring abort. The browser-visible body is exclusively `{success:true,connection:{state,qrDataUrl}}`, or a fixed safe failure envelope. Raw errors, keys/hash, sender, owner JID, provider bodies and pairing codes are not returned.

Native state `open` maps to connected; `close`/`disconnected`/`unauthenticated` map to disconnected; `connecting`/`qr` map to connecting; absent/unrecognized state remains unknown. Status requires exact nested instance identity. Connect handles the pinned build's flat QR shape without inventing identity; any explicit top-level or nested contradictory identity is refused. Already-open connect returns connected with no QR. Invalid/empty QR is unknown/no QR, not proof of disconnection. QR is bounded canonical standard-base64 PNG data URL text; this is not an image decode or proof that the account holder successfully scanned it.

## Browser handling

`EvolutionPairingCard` invokes only the project Edge function through `clientRuntime`, the same runtime client used by the existing administrator session/login. The card may read status on mount; only an explicit button requests connect/QR. Same-frame duplicate connect is fenced. Already connected sessions are preserved; no disconnect/reset/delete control is added by this slice.

The QR exists only in transient component display memory. It is not duplicated in the retained connection-state object, placed in a query cache, browser storage, logs or analytics. Close/unmount/auth changes/new requests/errors/local expiry discard it; generation fencing prevents a late connect answer reopening it after sign-out. The 60000 ms display lifetime is local, not a statement that the provider invalidated the QR. Server error text is dropped in favor of fixed messages. The existing Postora settings/actions remain unchanged apart from mounting the new card; their five pre-existing explicit-any lint violations are reported separately, not relabeled as passing.

## Connection-only webhook

`whatsapp-pairing-webhook` authenticates independent `CUREMED_EVOLUTION_WEBHOOK_SECRET` in `x-curemed-webhook-key` before reading JSON. An empty/missing configured secret fails closed. Body is limited to 32768 bytes and a 10000 ms read fence; abort/overflow/malformed input fails safely. Required own fields are exactly `instance:'curemed'` and `event:'connection.update'`. Foreign instances, other events and QR/message payloads are refused. Native `apikey`, `sender`, `destination`, `server_url` and arbitrary object-prototype-shaped keys are not copied into authority or returned. Secret comparison is the existing shared constant-time helper, exported without changing its behavior. Origin validation similarly reuses a new read-only predicate over the unchanged shared CORS allowlist.

The receiver acknowledges only. It writes no database/readiness/generation row and cannot activate messages or reopen a session on replay. The screen's status is read from the scoped native status operation. Generation-aware persistent ingestion remains separate unfinished full WhatsApp scope; this acknowledgement is not its replacement. Native webhook header forwarding is source-backed, not a new live transport proof. No webhook has been enabled by this checkpoint.

## Deployment contract and gates

Repository `config.toml` and example Edge manifest now describe both function names. The manifest appends the two deployment directories, three backend configuration names and a preflight smoke; `_shared` was already registered, and `main` remains excluded. Existing manifest values/entries are semantically unchanged. The deployed router does not consume manifest `verifyJwt` metadata, so these files alone are **not** router admission/deployment proof.

Consume only `/root/curemed-evolution-projects-20261104/curemedkw.private.json` inside a trusted operator process. Map its `api_key` to `CUREMED_EVOLUTION_API_KEY`, independent `webhook_secret` to `CUREMED_EVOLUTION_WEBHOOK_SECRET`, and set `CUREMED_EVOLUTION_URL` explicitly to `http://curemed-evolution:8080`. The shared provisioning bundle's generic service-DNS origin is not a reason to relax this fixed-origin check. Do not read file values into chat/tool output, use Romani's file, put keys in VITE/browser configuration, or copy the master repair bundle into either application.

Before production deployment: obtain exact source review/release approval; isolate the QR release from the pending integration migrations; verify live router admission/hash and copy only reviewed function/shared deltas without replacing `main`; privately seed/compare the actual backend scoped token; prove deployed auth and foreign-instance denial; retain executable website/function rollback assets. Device proof uses the designated Curemed account/operator, separately from Romani. No customer message, shipment, payment, bulk/history or Ministry-hold change follows from pairing.

Before enabling either project's webhook, the shared gateway's logging must be hardened through its reviewed managed configuration/reload packet. The pinned build defaults LOG_LEVEL to include WEBHOOKS when unset and logs native webhookData containing the instance key. Both project webhooks remain disabled. Provider QR logging and restart/session retention also require the pinned-source/operator check before real pairing. At preparation, the Curemed SSH connector became unavailable; this is an operator-route gap, not proof the existing gateway failed. No alternative host, rotation, reload or silent bypass was used.

An application rollback removes only the reviewed card/function/configuration changes; it must preserve both instance records, scoped credentials, histories and session/database volumes. Do not logout/delete/recreate an instance or restore an old whole database over a subsequently paired session. Full shared-payment/provider migration/activation/worker/message automation and the broader application rollback remain open work.
